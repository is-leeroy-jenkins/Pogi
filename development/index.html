    Development¶

    Pogi is a Streamlit-based analytics workbench for federal budget execution and account-balance analysis. Development work should preserve the existing analytical workflow while gradually improving maintainability, documentation quality, validation coverage, and MkDocs build reliability.

    The current project is intentionally simple: the main application logic lives in app.py, dependencies are listed in requirements.txt, and the documentation site is built from the docs/ directory using MkDocs Material. This structure is easy to run and inspect, but development changes should be made carefully because the Streamlit interface, data preparation logic, analytical helpers, model training workflow, and diagnostics currently share one source file.

    🧭 Purpose¶

    This page documents the recommended development workflow for Pogi.

    It covers:

    1. Local environment setup.
    2. Streamlit application execution.
    3. MkDocs documentation generation.
    4. Source documentation standards.
    5. Validation commands.
    6. Testing expectations.
    7. Build troubleshooting.
    8. Future refactoring guidance.
    9. GitHub Pages deployment preparation.

    The goal is to keep Pogi reliable, explainable, and documentation-ready as the application evolves.

    🐍 Python Environment¶

    Use a virtual environment for local development.

    Windows PowerShell¶

    python -m venv .venv
.\.venv\Scripts\Activate.ps1

    macOS or Linux¶

    python3 -m venv .venv
source .venv/bin/activate

    After activation, upgrade core packaging tools.

    python -m pip install --upgrade pip setuptools wheel

    Install the project dependencies.

    pip install -r requirements.txt

    📦 Dependency Groups¶

    Pogi uses one dependency file for both the Streamlit app and documentation tooling.

    Package Group Examples Purpose
    Application framework Streamlit, streamlit-extras Interactive web application
    Data analysis pandas, numpy Dataframe and numeric operations
    Statistics scipy Normality tests, probability plots, statistical calculations
    Machine learning scikit-learn Models, preprocessing, anomaly detection, metrics
    Visualization matplotlib, seaborn Charts, heatmaps, diagnostic plots
    Excel support openpyxl Workbook ingestion
    Documentation mkdocs, mkdocs-material, mkdocstrings, mkdocs-autorefs, pymdown-extensions Static documentation site
    Formatting black Python formatting support

    When adding dependencies, update requirements.txt and document the reason for the dependency in this page or the relevant user-guide page.

    ▶️ Running the Streamlit Application¶

    From the project root, run:

    streamlit run app.py

    Streamlit usually serves the application at:

    http://localhost:8501

    The application should open with:

    1. A Pogi logo or favicon.
    2. Global controls in the sidebar.
    3. A main header for the analytics workbench.

    4. Eight tabs:

      • Data Overview
      • Descriptive Statistics
      • Inferential Statistics
      • Feature Analysis
      • Feature Engineering
      • Anomaly Detection
      • Modeling
      • Diagnostics

    🧪 Development Smoke Test¶

    After source changes, run a basic manual smoke test:

    1. Start the app with streamlit run app.py.
    2. Confirm fallback data loads when enabled.
    3. Disable fallback data and confirm the upload control appears.
    4. Upload a CSV or Excel workbook.
    5. Confirm worksheet selection appears for multi-sheet workbooks.
    6. Confirm the Data Overview tab displays rows, columns, numeric columns, and categorical columns.
    7. Confirm the Descriptive Statistics tab can render a numeric profile.
    8. Build a feature matrix in the Feature Engineering tab.
    9. Train at least one model in the Modeling tab.
    10. Confirm the Diagnostics tab receives the model payload.

    This smoke test verifies the main Streamlit state handoff:

    Feature Engineering
└── st.session_state["feature_matrix"]

Modeling
└── st.session_state["last_model_payload"]

Diagnostics
└── consumes st.session_state["last_model_payload"]

    🧾 Documentation Build Workflow¶

    Pogi uses MkDocs Material for documentation.

    Build the documentation site from the project root:

    mkdocs build

    Preview the site locally:

    mkdocs serve

    The local preview usually runs at:

    http://127.0.0.1:8000

    The generated static site is written to:

    site/

    Do not manually edit files inside site/. Update the source Markdown files under docs/ instead.

    🧩 MkDocs Configuration Expectations¶

    The mkdocs.yml file should include:

    Section Purpose
    site_name Names the documentation site
    site_description Describes the project
    site_author Identifies the documentation author
    site_url Supports GitHub Pages deployment
    repo_url Links documentation to the repository
    theme Configures Material for MkDocs
    plugins Enables search and mkdocstrings
    markdown_extensions Enables admonitions, tables, details, code highlighting, and tabs
    extra_css Loads Pogi documentation CSS
    extra_javascript Loads Pogi documentation JavaScript
    nav Defines the left/top documentation navigation

    The navigation should match the actual files under docs/.

    🧬 Source Documentation Standard¶

    All public functions should use Google-style docstrings compatible with MkDocs, mkdocstrings, and griffe.

    Use this structure:

    """Short summary.

Purpose:
    Explain what the function does, what workflow stage it supports, and what
    state or data it prepares, modifies, or returns.

Args:
    name: Description of the argument.

Returns:
    ReturnType: Description of the returned value.

Raises:
    ExceptionType: Description of when the exception is raised.
"""

    Use only applicable sections. Do not add a Returns: section to procedures that do not return a meaningful value.

    ✅ Griffe-Compatible Docstring Rules¶

    Follow these rules to avoid MkDocs and griffe warnings:

    Rule Required Practice
    Section names Use Purpose:, Args:, Returns:, Raises:, Notes:, Examples:
    Argument names Every Args: entry must match the real function parameter name
    Return type Returns: entries must include an explicit type when needed
    No underline sections Do not use Purpose: ----- or Parameters: -----
    No self docs Do not document self or cls
    No placeholder text Avoid vague descriptions such as “value used by the operation”
    No fake behavior Do not document behavior that the source does not implement
    No narration Comments should document the function, not explain that documentation was added

    Good example:

    def feature_quality(df: pd.DataFrame) -> pd.DataFrame:
    """Compute feature quality metrics.

    Purpose:
        Computes completeness, uniqueness, cardinality ratio, variance, and entropy
        metrics for each dataframe column. The resulting profile supports the Data
        Overview tab and helps identify missingness, high-cardinality fields, and
        low-information columns before modeling.

    Args:
        df: Source dataframe to profile.

    Returns:
        pd.DataFrame: Feature quality table sorted by completeness and cardinality ratio.
    """

    🧹 Source Preservation Rules¶

    When modifying app.py, preserve executable behavior unless a behavior change is explicitly required.

    Do not casually change:

    1. Imports.
    2. Constants.
    3. Function names.
    4. Function signatures.
    5. Type annotations.
    6. Streamlit session-state keys.
    7. Sidebar controls.
    8. Tab names.
    9. Model dictionaries.
    10. Estimator parameters.
    11. Feature-engineering logic.
    12. Anomaly-voting logic.
    13. Diagnostic payload structure.
    14. Plotting behavior.
    15. Fallback file paths.

    The current application has a working tab sequence. Documentation improvements should not break that sequence.

    🧠 Session State Contract¶

    Pogi uses Streamlit session state for cross-tab workflow continuity.

    Session Key Producer Consumer Purpose
    feature_matrix Feature Engineering tab Modeling tab Stores engineered features
    anomaly_flags Anomaly Detection tab User review and potential downstream use Stores detector outputs and anomaly votes
    last_model_payload Modeling tab Diagnostics tab Stores trained model, predictions, test data, feature names, and task type

    Any change to these keys must be treated as a breaking change unless all dependent tabs are updated together.

    🧪 Python Validation Commands¶

    Run these commands from the project root.

    Compile the main app:

    python -m py_compile .\app.py

    Compile the full project:

    python -m compileall .

    Check whether the module can be imported:

    python -c "import app; print('app import ok')"

    For Streamlit applications, import checks may be affected by top-level Streamlit execution. If importing app causes issues during MkDocs API generation, consider extracting pure helper functions into a documentation-safe module.

    📘 MkDocs Validation Commands¶

    Run the documentation build:

    mkdocs build

    Serve locally:

    mkdocs serve

    Build with a clean output directory:

    mkdocs build --clean

    The build should complete without missing-nav warnings, unlisted-page warnings, or avoidable griffe warnings.

    🔍 Common MkDocs Build Issues¶

    Build Message Likely Cause Fix
    Page listed in nav but not found File does not exist under docs/ Create the missing file or remove the nav entry
    Page exists but is not in nav File exists but is not listed Add the file to mkdocs.yml or remove the unused file
    mkdocstrings import failure app.py executes Streamlit code at import time Move pure helper functions into a documentation-safe module
    Griffe failed to parse name-description pair Bad Args: or Attributes: formatting Rewrite docstring section using name: description
    No type or annotation for returned value Return documentation is incomplete Add a return annotation or explicit return type in Returns:
    CSS not loading Incorrect extra_css path Confirm path is relative to docs/
    JavaScript not loading Incorrect extra_javascript path Confirm path is relative to docs/

    Do not hide build problems by removing API pages unless the goal is a temporary diagnostic build.

    🧰 Recommended Development Sequence¶

    Use this sequence for normal development:

    1. Create or activate the virtual environment.
    2. Install dependencies from requirements.txt.
    3. Run the Streamlit app.
    4. Confirm fallback data loads.
    5. Make one source or documentation change at a time.
    6. Run python -m py_compile .\app.py.
    7. Run mkdocs build.
    8. Fix warnings before making unrelated changes.
    9. Preview with mkdocs serve.
    10. Commit source and documentation changes together.

    🧱 Recommended Future Refactor¶

    If Pogi continues to grow, the best next step is to separate pure analytical logic from Streamlit UI execution.

    Recommended future layout:

    pogi/
├── __init__.py
├── data.py
├── profiling.py
├── statistics.py
├── features.py
├── anomalies.py
├── modeling.py
├── diagnostics.py
├── plotting.py
└── ui.py

app.py

    Recommended module responsibilities:

    Module Responsibility
    data.py File loading, worksheet discovery, fallback loading, numeric coercion
    profiling.py Feature quality, missingness, descriptive profile
    statistics.py Correlations, p-values, normality testing, group comparisons, VIF
    features.py Imputation, scaling, winsorization, categorical encoding
    anomalies.py Isolation Forest, Local Outlier Factor, PCA-distance anomaly voting
    modeling.py Regression and classification model setup, fitting, and comparison
    diagnostics.py Residual analysis, confusion matrix, ROC/PR curves, permutation importance
    plotting.py Shared Matplotlib/Seaborn formatting helpers
    ui.py Streamlit layout and tab orchestration
    app.py Thin application entry point

    This refactor would make the project easier to test, document, and maintain. It should be performed only after the current documentation site builds cleanly.

    🧪 Testing Roadmap¶

    Pogi currently relies primarily on manual validation. A future test suite should focus first on pure helper functions.

    Recommended initial tests:

    Function Area Test Focus
    Numeric coercion Commas, dollar signs, blanks, dashes, parentheses, parse thresholds
    Humanized numbers K/M/B/T suffixes and small-number formatting
    Feature quality Completeness, uniqueness, variance, entropy
    Descriptive profile Percentiles, missingness, outlier rates
    Correlations Pearson, Spearman, Kendall outputs
    VIF Multicollinearity calculations
    Data loading CSV and Excel parsing behavior
    Session payloads Feature matrix and model diagnostic payload shape

    Suggested future test directory:

    tests/
├── test_data.py
├── test_profiling.py
├── test_statistics.py
├── test_features.py
└── test_modeling.py

    🧾 Formatting Guidance¶

    Use Black for Python formatting.

    black app.py

    Before formatting large files, confirm the formatter will not disturb intentionally aligned Streamlit layout blocks. If formatting changes are too broad, isolate them in a separate commit from functional changes.

    Recommended practice:

    1. Make functional changes.
    2. Validate behavior.
    3. Format source.
    4. Re-run validation.
    5. Build documentation.

    🖼️ CSS and JavaScript Assets¶

    Project-specific documentation styling should live under:

    docs/assets/css/pogi.css

    Project-specific documentation JavaScript should live under:

    docs/assets/js/pogi.js

    The CSS should support:

    1. Dark-mode documentation.
    2. Dark blue header and tabs.
    3. Readable tables.
    4. Readable code blocks.
    5. Mkdocstrings API cards.
    6. Rounded images and diagrams.
    7. Accessible contrast.

    The JavaScript should remain lightweight and progressive. It may add:

    1. Back-to-top control.
    2. API filtering.
    3. Code block labels.
    4. Section-link copy controls.
    5. Table filtering for large tables.

    Avoid analytics, remote calls, popups, heavy frameworks, or decorative animations.

    🚀 GitHub Pages Deployment¶

    After the documentation builds cleanly, Pogi can be published through GitHub Pages.

    Typical deployment options:

    Option Description
    mkdocs gh-deploy Builds and pushes the static site to the gh-pages branch
    GitHub Actions Builds documentation automatically on push
    Manual site upload Not recommended unless required

    For manual deployment using MkDocs:

    mkdocs gh-deploy

    Before deploying, verify:

    1. site_url is correct in mkdocs.yml.
    2. repo_url is correct in mkdocs.yml.
    3. mkdocs build succeeds locally.
    4. All pages in nav exist.
    5. All images and assets render locally.
    6. API pages render without griffe warnings.
    7. No generated site/ files are manually edited.

    🛡️ Development Guardrails¶

    Use these guardrails for future changes.

    Guardrail Reason
    Preserve tab order Keeps documentation aligned with the application
    Preserve session-state keys Prevents downstream tab failures
    Preserve fallback path Keeps demos and local testing stable
    Preserve model dictionaries unless intentionally changing capabilities Prevents silent feature loss
    Preserve diagnostic payload shape Keeps Diagnostics tab functional
    Validate docstrings before building API pages Prevents griffe warnings
    Run mkdocs build after documentation changes Confirms navigation and rendering
    Avoid undocumented source behavior Keeps user guide and API docs aligned

    📌 Summary¶

    Pogi development should prioritize stability, source preservation, and documentation reliability. The current single-file Streamlit architecture is effective for rapid iteration and local analytical workflows, but it requires careful validation because UI logic, analytical helpers, model orchestration, and diagnostics are tightly coupled.

    The recommended development pattern is simple: make focused changes, preserve existing behavior, compile the source, build the documentation, fix warnings immediately, and keep the user guide aligned with the actual Streamlit workflow.
